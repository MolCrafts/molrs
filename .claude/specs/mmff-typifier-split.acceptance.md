# Acceptance criteria

- **ac-001 / ac-002 / ac-009 (code)** — 形状与可达性。owner 的定案是合同：一个引擎、两扇具名门面、零 variant 旗标。ac-002 是防回归的源码门禁：硬编码一旦回来，`MMFF94STypifier` 就会再次静默产出 MMFF94 参数——正是本 spec 要关掉的缺口。ac-009 是 `chem-perceive-14-all-tables` 的解锁条件。
- **ac-003 / ac-004 (code)** — 两条参数路径各自的区分性。ac-003 盯路径 1（烘焙进 Frame 的 `koop`，内核实际读的就是它）；ac-004 盯路径 2（XML → ForceField 树）。只满足其中一条，`MMFF94STypifier` 仍是半个谎言。
- **ac-005 (runtime)** — 端到端，并自带**非空洞护栏**：ethane / benzene 上两者必须完全一致。没有这条，区分性测试可能靠一个根本不存在的差异侥幸通过。
- **ac-006 (runtime)** — 这是管线的重接线，不是 MMFF94 的重新参数化；任何被改动的数值字面量都是红旗。
- **ac-007 (runtime)** — Python 是用户面；轮子必须重建，否则测试会对着旧 `.so` 撒谎。
- **ac-008 (code)** — `MmffVariant` 那条"表还不在"的注释**已经骗过一轮读者**（本 spec 起草时据它误判 MMFF94s 是缺口）；它和 rustdoc 门禁一起收口。
